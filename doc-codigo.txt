Descripción detallada de la implementación

La solución desarrollada se compone de tres bloques principales de código

Un servidor central en Node.js con Socket.IO (servidorserver.js), que actúa como coordinador concurrente de las partidas.

Un servicio de comunicación en Flutter (libservicessocket_service.dart), que encapsula la lógica de red, estado y temporizador de turnos.

Una pantalla de interfaz de usuario en Flutter (libscreensbattle_screen.dart), que permite la interacción del jugador y visualiza el estado de la batalla.

A continuación se describe en detalle el funcionamiento de cada uno, destacando explícitamente los aspectos de concurrencia, sincronización y manejo de eventos.

1. Servidor concurrente en Node.js (servidorserver.js)
1.1. Inicialización del servidor HTTP y Socket.IO

El servidor se construye sobre tres componentes

Express framework HTTP mínimo para exponer endpoints simples (por ejemplo, status).

Servidor HTTP nativo de Node base sobre la que se monta Socket.IO.

Socket.IO capa de comunicación bidireccional en tiempo real basada en WebSockets.

Fragmento conceptual

const express = require('express');
const http = require('http');
const { Server } = require('socket.io');
const cors = require('cors');

const app = express();
app.use(cors());

const server = http.createServer(app);
const io = new Server(server, {
  cors {
    origin '',
  },
});


Con esto, cualquier cliente autorizado puede conectarse por WebSockets al mismo host y puerto donde corre el servidor (por ejemplo, httpIP3000).

Además, se define una constante global

const TURN_DURATION_MS = 10000;


que representa la duración lógica de cada turno (10 segundos). Esta constante se utiliza tanto para el timeout del lado del servidor como para informar al cliente sobre la duración del turno.

1.2. Clase Partida proceso concurrente lógico por sala

El núcleo de la lógica concurrente del servidor se encuentra en la clase Partida, que modela cada sala (roomId) como un proceso independiente con su propio estado y sus propios eventos.

class Partida {
  constructor(roomId) {
    this.roomId = roomId;

    this.estado = {
      vidaA 100,
      vidaB 100,
      energiaA 100,
      energiaB 100,
      turno 1,
    };

    this.accionesPendientes = {};  { JugadorA 'atacar', JugadorB 'curar' }
    this.timeoutId = null;
    this.jugadores = new Set();
  }
}


Elementos clave

roomId identifica de manera única la sala de juego.

estado agrupa todas las variables compartidas de la partida (vidas, energía, turno).

accionesPendientes almacena las acciones declaradas por cada jugador durante el turno actual.

timeoutId referencia al timeout activo del turno (si lo hay).

jugadores conjunto de jugadores que han participado en la partida.

Esta encapsulación permite que cada Partida evolucione de forma independiente de las demás, lo que es un ejemplo claro de concurrencia a nivel de procesos lógicos dentro del servidor.

1.3. Registro de jugadores y sincronización de estado

Cuando un jugador se une a una sala, el servidor registra su presencia y sincroniza el estado actual

registrarJugador(jugador) {
  this.jugadores.add(jugador);
}

enviarEstadoActual(socket) {
  socket.emit('estado_partida', {
    roomId this.roomId,
    estado this.estado,
    turno this.estado.turno,
  });
}


registrarJugador añade el nombre del jugador al conjunto de participantes.

enviarEstadoActual envía al cliente una foto del estado actual de la partida.
Esto es fundamental para soportar reconexiones o ingreso tardío a una partida en curso.

1.4. Registro de acciones y comienzo del timeout del turno

El método registrarAccion es el responsable de manejar la lógica de concurrencia a nivel de turno

registrarAccion(jugador, accion, io) {
   Evitamos acciones duplicadas en un mismo turno
  if (this.accionesPendientes[jugador]) {
    return;
  }

  this.accionesPendientes[jugador] = accion;

   Si es la primera acción, arrancamos timeout de turno
  if (!this.timeoutId) {
    this.iniciarTimeout(io);
  }

   Si ya recibimos acciones de ambos jugadores, resolvemos antes del timeout
  if (Object.keys(this.accionesPendientes).length = 2) {
    this.resolverTurno(io, false);
  }
}


Comportamiento

Si un jugador ya envió una acción en el turno actual, la nueva es ignorada (protección contra duplicaciones).

Si esta es la primera acción del turno

se arranca un timeout (temporizador) que garantiza que el turno se resolverá aunque el otro jugador no responda.

Si ya se recibieron acciones de ambos jugadores

se llama inmediatamente a resolverTurno, sin esperar al timeout.

Interpretación concurrente
El servidor no bloquea la ejecución global; en cambio, usa eventos y temporizadores para coordinar cuándo resolver el turno. Existen dos caminos paralelos hacia la resolución

Ambas acciones llegan antes del timeout.

No llegan las dos acciones y el timeout fuerza una acción por defecto.

1.5. Timeout de turno y acciones por defecto

La función iniciarTimeout implementa un mecanismo de progreso garantizado

iniciarTimeout(io) {
  this.timeoutId = setTimeout(() = {
    if (!this.accionesPendientes['JugadorA']) {
      this.accionesPendientes['JugadorA'] = 'defender';
    }
    if (!this.accionesPendientes['JugadorB']) {
      this.accionesPendientes['JugadorB'] = 'defender';
    }
    this.resolverTurno(io, true);
  }, TURN_DURATION_MS);
}


Si pasado el tiempo máximo del turno

Algún jugador no envió su acción,

el servidor le asigna por defecto la acción defender,

y procede a resolver el turno con la bandera porTimeout = true.

Esto evita deadlocks y demuestra un uso explícito de timeouts como herramienta de control concurrente.

1.6. Resolución del turno y actualización del estado

La lógica de resolución de turno combina las acciones de ambos jugadores y actualiza el estado de la partida

resolverTurno(io, porTimeout) {
  if (this.timeoutId) {
    clearTimeout(this.timeoutId);
    this.timeoutId = null;
  }

  const acciones = this.accionesPendientes;
  const logTurno = [];

  const accionA = acciones['JugadorA']  'defender';
  const accionB = acciones['JugadorB']  'defender';

  logTurno.push(`Turno ${this.estado.turno} A=${accionA}, B=${accionB}`);

   Lógica de combate simplificada (A sobre B)
   ...

  if (porTimeout) {
    logTurno.push('⚠️ Turno resuelto por timeout (acciones por defecto para jugadores inactivos).');
  }

  this.estado.energiaA = Math.min(100, this.estado.energiaA + 10);
  this.estado.energiaB = Math.min(100, this.estado.energiaB + 10);

  this.estado.turno += 1;
  this.accionesPendientes = {};

  io.to(this.roomId).emit('resultado_turno', {
    roomId this.roomId,
    estado this.estado,
    log logTurno,
    porTimeout,
    turno this.estado.turno - 1,
    turnDurationMs TURN_DURATION_MS,
  });
}


Aspectos importantes

Se cancela el timeout activo para evitar que dispare luego de resolver.

Se registran las acciones efectivas de ambos jugadores, con defender como fallback.

Se calcula el daño y la curación según las acciones.

Se incrementa el número de turno y se limpian las acciones pendientes.

Se emite el resultado del turno a todos los clientes de la sala mediante io.to(this.roomId).emit(...).

Esto representa un punto de sincronización el servidor combina acciones concurrentes, resuelve y luego vuelve a un estado “esperando nuevas acciones”.

1.7. Gestión de múltiples partidas concurrentes

El servidor mantiene un mapa de partidas

const partidas = new Map();

function obtenerPartida(roomId) {
  if (!partidas.has(roomId)) {
    partidas.set(roomId, new Partida(roomId));
  }
  return partidas.get(roomId);
}


Cada roomId corresponde a una instancia de Partida.

Esto permite tener múltiples partidas activas en paralelo, lo que añade un nivel de concurrencia extra concurrencia entre jugadores dentro de una partida y concurrencia entre partidas distintas gestionadas por el mismo servidor.

1.8. Eventos de Socket.IO conexión, unión a partida y acciones
io.on('connection', (socket) = {
  console.log('🔌 Nuevo cliente conectado', socket.id);

  socket.on('unirse_partida', ({ roomId, jugador }) = {
    const partida = obtenerPartida(roomId);
    partida.registrarJugador(jugador);
    socket.join(roomId);
    partida.enviarEstadoActual(socket);
  });

  socket.on('accion', (data) = {
    const { roomId, jugador, accion } = data;
    const partida = partidas.get(roomId);
    if (!partida) return;
    partida.registrarAccion(jugador, accion, io);
  });

  socket.on('disconnect', () = {
    console.log('❌ Cliente desconectado', socket.id);
  });
});


connection evento cuando un cliente se conecta al servidor.

unirse_partida asocia el socket a una sala de juego y sincroniza el estado actual.

accion recibe acciones de los clientes y delega en Partida la lógica concurrente.

disconnect loguea la desconexión; la partida permanece en memoria para permitir reconexión.

2. Servicio de comunicación en Flutter (libservicessocket_service.dart)

Este servicio encapsula la lógica de red, estado y temporización del lado del cliente. Se implementa como un ChangeNotifier para integrarse con Provider.

2.1. Estado interno del servicio
class SocketService with ChangeNotifier {
  IO.Socket socket;
  bool conectado = false;
  bool intentandoReconectar = false;

  String log = ;

  MapString, dynamic estado = {
    vidaA 100,
    vidaB 100,
    energiaA 100,
    energiaB 100,
    turno 1,
  };

  String _ultimoJugador;
  String _ultimaRoomId;

  final int turnDurationMs = 10000;
  int segundosRestantes = 0;
  Timer _turnTimer;
}


Campos relevantes

socket conexión WebSocket (Socket.IO) activa.

conectado  intentandoReconectar flags para la UI.

log texto que el usuario ve en el panel de consola.

estado copia local del estado de la partida (sincronizado con el servidor).

_ultimoJugador  _ultimaRoomId permiten reconectar sin reingresar datos.

segundosRestantes y _turnTimer manejan el temporizador de turno concurrente en el cliente.

2.2. Establecimiento de conexión y unión a la partida
void conectar(String jugador, String roomId) {
  _ultimoJugador = jugador;
  _ultimaRoomId = roomId;

  socket.dispose();

  socket = IO.io(
    'http10.0.2.23000',
    String, dynamic{
      'transports' ['websocket'],
      'autoConnect' false,
    },
  );

  socket!.onConnect((_) {
    conectado = true;
    intentandoReconectar = false;
    log += 🟢 Conectado al servidor como $jugador en sala $roomIdn;
    socket!.emit(unirse_partida, {roomId roomId, jugador jugador});
    notifyListeners();
  });


Se configura la conexión hacia el servidor (10.0.2.2 en emulador).

Al conectarse, se emite inmediatamente el evento unirse_partida y se actualiza el estado visual.

2.3. Manejo de desconexión y reconexión
socket!.onDisconnect((_) {
  conectado = false;
  intentandoReconectar = true;
  _detenerTurnTimer();
  log += 🔴 Desconectado del servidor. Podés intentar reconectar.n;
  notifyListeners();
});

void reconectar() {
  if (_ultimoJugador != null && _ultimaRoomId != null) {
    log += ♻️ Intentando reconectar como $_ultimoJugador en sala $_ultimaRoomId...n;
    notifyListeners();
    conectar(_ultimoJugador!, _ultimaRoomId!);
  }
}


Cuando la conexión se pierde

se detiene el temporizador del turno,

se activa el modo de reconexión.

reconectar reutiliza los datos recordados para restablecer la conexión y re-unirse a la partida.

Esto aporta robustez frente a fallos de red y es un ejemplo de manejo de fallas en sistemas concurrentes.

2.4. Sincronización del estado de partida
socket!.on(estado_partida, (data) {
  estado = MapString, dynamic.from(data[estado]);
  log += 📦 Estado de partida sincronizado (turno ${estado[turno]}).n;
  _iniciarTurnTimer();
  notifyListeners();
});

socket!.on(resultado_turno, (data) {
  estado = MapString, dynamic.from(data[estado]);

  log += n🎯 Resultado turno ${data[turno]}n;
  if (data[log] is List) {
    for (var linea in data[log]) {
      log +=    • $linean;
    }
  }

  _iniciarTurnTimer();
  notifyListeners();
});


estado_partida se usa al unirse o reconectarse; el cliente se alinea con el servidor (consistencia).

resultado_turno se recibe tras la resolución concurrente en el servidor; actualiza el estado local y el log.

En ambos casos se llama a _iniciarTurnTimer, que permite visualizar gráficamente el tiempo del siguiente turno.

2.5. Envío de acciones
void enviarAccion(String roomId, String jugador, String accion) {
  if (!conectado  socket == null) return;

  socket!.emit(accion, {
    roomId roomId,
    jugador jugador,
    accion accion,
  });

  log += ⚔️ $jugador elige acción $accionn;
  notifyListeners();
}


El cliente emite una acción al servidor sin bloquearse; la resolución queda del lado del backend.

El log registra inmediatamente la acción para feedback al usuario.

2.6. Temporizador de turno en el cliente
void _iniciarTurnTimer() {
  _detenerTurnTimer();
  segundosRestantes = (turnDurationMs  1000).round();

  _turnTimer = Timer.periodic(const Duration(seconds 1), (timer) {
    segundosRestantes--;
    if (segundosRestantes = 0) {
      segundosRestantes = 0;
      _detenerTurnTimer();
    }
    notifyListeners();
  });

  notifyListeners();
}


Cada vez que se inicia un turno, el cliente arranca un Timer.periodic que se ejecuta concurrentemente con la UI.

El temporizador no bloquea la interfaz; solo decrementa segundosRestantes y dispara notifyListeners() para actualizar la barra de progreso.

Este es un ejemplo concreto de concurrencia interna en el cliente la lógica del temporizador y la lógica de entrada de usuario (tocar botones, etc.) coexisten y se coordinan por medio del estado compartido.

3. Interfaz de usuario en Flutter (libscreensbattle_screen.dart)

Por último, la pantalla BattleScreen consume el servicio SocketService mediante Provider y ofrece la interacción con el jugador.

La pantalla muestra

TextField para elegir el nombre de usuario.

Botón para conectarse al servidor.

Botón opcional para reconectar si se detectó desconexión.

Estado textual de conexión (Conectado, Desconectado, etc.).

Todo esto se alimenta del estado expuesto por SocketService (conectado, intentandoReconectar).

3.2. Visualización del timer concurrente

Se define un widget _buildTurnTimer que renderiza una barra de progreso y el número de segundos restantes

Utiliza segundosRestantes del servicio.

Muestra una barra que se acorta con el tiempo.

Cambia de color cuando el tiempo está por terminar.

Esto permite que el alumno visualice el tiempo de turno, reforzando la idea de que existe una ventana temporal limitada para decidir una acción, coordinada con el timeout del servidor.

3.3. Barras de vida y energía

La pantalla representa

Vida y energía del JugadorA.

Vida y energía del JugadorB.

Fondo gris.

Esto hace más claro el efecto de las acciones concurrentes resueltas en el servidor.

3.4. Botones de acción

Se presentan tres botones

Atacar

Cada botón invoca

El usuario no espera bloqueado una respuesta inmediata; en cambio

Síntesis del enfoque concurrente

Con el código actual, la aplicación implementa concurrencia en varios niveles

En el servidor Node.js

Cada sala (Partida) se comporta como un proceso concurrente lógico, con estado propio.

Las acciones de jugadores se gestionan de manera asincrónica via eventos de Socket.IO.

Se utiliza un timeout de turno para evitar bloqueos y garantizar progreso del sistema.

Se soportan múltiples partidas concurrentes a través de un mapa roomId → Partida.

En el cliente Flutter

Se ejecuta en paralelo la interacción del usuario y un temporizador de turno, coordinados con el servidor.

Se maneja la reconexión y la sincronización de estado (consistencia eventual) al recibir estado_partida.

El modelo reactivo (ChangeNotifier + Provider) permite actualizar UI en respuesta a eventos concurrentes (turnos, reconexiones, etc.).

En la interacción usuario–sistema

Los jugadores eligen acciones en paralelo.

La resolución ocurre de forma centralizada, pero sujeta a prioridades (orden de llegada, reglas de combate, timeout).

La experiencia de juego refleja de forma directa los efectos de la concurrencia (turnos simultáneos, cambios de vida, logs secuenciales).
